# 00-1 教师准备与验收

## 发布前准备

1. 明确每位学生使用**自己的** `software-engineering` 仓库，并决定是否要求私有仓库。不要要求学生公开真实姓名。
2. 公布仓库访问方式。若学生仓库为私有，说明如何授予教师查看权限；确认教师账号确实能打开学生仓库。本课程每项任务均提交到学生自己的 `main` 分支，并放在对应任务文件夹中。
3. 指定提交个人仓库链接的渠道，例如现有教学平台的作业入口，并记录“学生—GitHub 仓库链接”的对应关系。
4. 向学生提供统一的[任务总结模板](../任务总结模板.md)，并说明只需简短填写，不修改仓库根目录 `README.md`。
5. 在任务页中填入截止时间和求助渠道。先用一个学生视角的测试账号完整走通创建仓库、clone、commit、push 及授予教师访问权限的流程。
6. 预留账号、双重验证和校园网络问题的现场帮助；这些故障不应算作学生的编程错误。

## 反馈安排

检查学生仓库中的 `00-1-提交第一份代码` 文件夹、提交记录和 `任务总结.md`。可在课堂或教学平台给出简短反馈。若需要修改，学生直接更新自己的 `main` 分支，并再次提交仓库链接或告知教师。

## 验收标准

| 项目 | 通过表现 |
| --- | --- |
| 提交流程 | 学生在自己的仓库中完成 commit，并推送到 `main` |
| 仓库归属 | 学生提交自己的 GitHub 仓库链接 |
| 可访问性 | 教师能打开学生仓库并查看文件与提交记录 |
| 过程说明 | `任务总结.md` 简要记录程序结果及 `commit`、`push` 的区别；仓库根目录 `README.md` 保持不变 |
| 修改能力 | 根据反馈修改文件，并能再次提交到自己的仓库 |
| 个人解释 | 能用自己的话说明 commit、push 的作用，以及任务成果为何按文件夹整理 |

本任务建议采用“通过／补做”评价。工具安装和账号问题提供补做机会。此处不评价 Python 语法熟练度，也不要求每位学生必须使用 AI；评价重点是学生能否判断和验证 AI 的建议。
