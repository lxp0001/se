# 阶段 04：故障排查手册

本文整理 Docker、GitHub Actions、GitHub Pages 和 Railway 部署时常见的问题。排查时先确认正在查看的分支和部署提交，再根据错误出现的步骤处理。

## GitHub Actions

### 工作目录不存在，路径里重复出现仓库名

GitHub Actions 的 `working-directory` 和 `paths` 都相对于仓库检出目录，不要再加一层仓库名。例如仓库中的目录是：

```text
stage-04/04-1-Docker打包与本地运行/starter/app
```

工作流就应使用该相对路径；不要写成 `se/stage-04/...`。出现 `/home/runner/work/se/se/se/...` 一类路径时，检查并去掉多余的 `se/`。同时确认 `working-directory` 指向的目录确实存在。

### 提示 Action 将从 Node.js 20 改用 Node.js 24

这是 Action 自身运行时的弃用警告，不等同于项目构建失败。更新工作流中使用的 Action 主版本，例如本仓库使用 `actions/checkout@v5`、`actions/setup-node@v5` 和 `actions/configure-pages@v6`。`setup-node` 的 `node-version` 是项目构建使用的 Node 版本，与 Action 自身的运行时是两回事。

## GitHub Pages 与前端

### Pages 地址显示 404 / Site not found

依次确认：

1. 修改已推送到 GitHub 上用于部署的分支。
2. 仓库 **Settings → Pages → Build and deployment → Source** 设为 **GitHub Actions**。
3. **Actions** 中“部署前端到 GitHub Pages”工作流最近一次运行成功。
4. 上传的目录是前端构建产物 `frontend/dist`。普通项目仓库的地址是 `https://账号名.github.io/仓库名/`；用户站点仓库名为 `账号名.github.io`，访问地址是 `https://账号名.github.io/`。根据你实际部署的仓库类型访问，不要把示例仓库名照搬。

Pages 首次启用后需要成功完成一次部署，单有本地提交或工作流文件不会自动生成网站。

### 页面报 `React is not defined`

Vite 没有启用 React JSX 插件时，JSX 可能被编译成依赖全局 `React` 的代码。检查前端是否安装 `@vitejs/plugin-react`，并在 `vite.config.js` 中加载 `react()`；修改后重新构建和部署。

### Pages 页面无法连接 API

GitHub Pages 只托管静态文件，不能访问 Railway 的私有域名。前端必须配置一个公网 HTTPS API 地址。API 服务如果仅通过 Railway 私有网络开放，Pages 页面无法连接。

本仓库的 Railway API 域名可直接用于测试：

```text
https://se-production-2cc7.up.railway.app/events
https://se-production-2cc7.up.railway.app/docs
```

如果 fork/复制仓库或更换后端域名，要在**正在发布页面的那个仓库**中更新 Actions Variables 变量 `VITE_API_BASE_URL`，然后重新运行 Pages 部署工作流，使新地址编译进静态文件。GitHub 用户名、仓库名和 Railway 域名都应以你自己的页面显示值为准。

### 浏览器报 CORS / 预检请求没有 `Access-Control-Allow-Origin`

先确认 Railway 正在运行包含 FastAPI `CORSMiddleware` 的最新提交；再在 API 服务的 Variables 中设置：

```text
CORS_ORIGINS=https://账号名.github.io
```

只填写站点来源，不要加项目仓库路径、接口路径、端口或结尾斜杠。对 GitHub Pages 来说，来源是 `https://账号名.github.io`；即使页面完整地址为 `https://账号名.github.io/仓库名/`，CORS 值也不含 `/仓库名/`。如使用自定义域名，填浏览器地址栏中的协议和主机名。保存变量后要应用更改并重新部署 API。CORS 允许浏览器读取响应，不是 API 身份验证；公开的 API 写接口仍可能被其他客户端调用。

## Railway

### `Railpack could not determine how to build the app` / `start.sh not found`

查看构建日志中 Railpack 列出的文件。如果只看到 `.github/`、`stage-00/`、`stage-04/` 等仓库顶层目录，说明 Railway 正在分析整个仓库，没有进入后端目录。

对于本仓库的 API 服务，在 **Settings → Build → Root Directory** 中设置：

```text
/stage-04/04-1-Docker打包与本地运行/starter/app/backend
```

清空误填的 `Build Command` 或 `Start Command`（例如 `start.sh`），让 Railway 使用该目录下的 `Dockerfile`。日志应显示检测并使用 Dockerfile。该后端 Dockerfile 已定义 Uvicorn 启动命令，不需要额外的 `start.sh`。

### 服务画布里找不到名为 `api` 的卡片

Railway 服务名称由创建者设定，不会根据目录自动命名。画布中可能只有名为 `se` 的服务；点击服务卡片检查它的 **Root Directory**、构建日志和部署状态。若要分别部署前后端，需要分别创建服务并设置各自的根目录。

### Railway 显示免费方案资源配置额度不足

该提示表示当前工作区或方案暂时无法为新服务分配资源。先查看用量和现有服务，确认不再需要后再停止或删除；也可以等待额度恢复或使用其他托管平台。删除项目会永久删除其中的服务、部署、环境和数据，删除前确认备份。不要在未核对费用前直接升级方案。

### API 域名上的 `8000` 是什么

`8000` 是 FastAPI 在容器内监听的端口。Railway 域名已映射到该端口，因此访问时通常不需要在域名后写 `:8000`。用 `/events` 检查 JSON 响应，用 `/docs` 打开 FastAPI 交互式文档。

## 发布后仍看到旧版本

- 检查 GitHub 上的部署分支是否包含目标提交。
- 在 Railway 的 Deployments 中确认实际部署的提交，并确认环境变量已应用。
- GitHub Pages 的前端改动需要 Pages 工作流成功完成；修改 `VITE_API_BASE_URL` 后要重新构建部署。
- 浏览器仍显示旧文件时，强制刷新页面后再检查。
